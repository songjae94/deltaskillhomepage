# 백엔드(/submit-update) 수리 인수인계 — 2026-08-12

> **이 세션에서 할 일**: Supabase에 직접 접속해 `/submit-update`가 `update_failed_delete`로
> 실패하는 원인을 확정하고, UPSERT 방식 핸들러로 교체·검증한다.
> 프론트엔드는 **이미 전부 대응돼 있다** (아래 §7) — 이 세션은 백엔드만 만지면 된다.

---

## 1. 문제 요약

- 학생이 저장한 회차를 **수정 후 재저장**하면 서버가 `update_failed_delete`로 실패.
- 현재 핸들러 구조: 기존 응답 30줄 **DELETE → 재INSERT**. 이 DELETE가 막힌다.
- 원인 후보(미확정): ① RLS 켜짐 + delete 정책 없음 ② FK RESTRICT ③ 키 권한 없음 ④ 트리거.
  - 함수가 `--no-verify-jwt`로 배포돼 있어 **service_role 클라이언트일 가능성**이 높고,
    그렇다면 ①③은 배제되어 ②④만 남는다. 진단 [0]으로 확정할 것.
- 해법: (submission_id, item_no) 기준 **UPSERT**로 교체. 단 UPSERT는 만능이 아니다 —
  anon+RLS 환경이면 UPDATE 정책도 필요하다. **원인 확정 전에는 배포하지 않는다.**

## 2. 확정된 사실 (코워크 배포문서 기준)

| 항목 | 값 |
|---|---|
| 프로젝트 | `cvlrphtupjmaefahodgz.supabase.co` |
| Edge Function | 이름 `api` 하나에 전 엔드포인트 분기 (`/enroll` `/login` `/submit` `/submit-update` `/history` `/submission` `/photo` `/photo-upload`) |
| 배포 옵션 | `--no-verify-jwt` |
| 인증 | 자체 토큰 `ds_tk` → RPC `auth_verify`로 검증. 소유권은 **전화번호(숫자만) 일치** 기준 |
| 테이블 | `public.submissions` (컬럼 `updated_at` 있음 — 기존 배포 A단계에서 추가) |
| 검증 규칙 | responses 1~40개, `my_answer` ≤20자, `memo` ≤500자, score 0~100 |

**미확인** (진단으로 채울 것): responses 실제 테이블명·FK 컬럼명·문항번호 컬럼명,
`/submit`이 넣는 전체 컬럼 목록, submissions에 phone이 직접 있는지(학생 테이블 경유인지),
DB 클라이언트가 service_role인지 anon인지.

## 3. ⚠️ 이번에 새로 발견한 것 — item_no 0

**직접입력(자유 시험) 저장은 `item_no: 0` 메타 레코드를 보낸다.**
(과목·날짜·시험명을 memo에 담는 0번 행. exam_code는 `자유:이름` 형태)

코워크 0812 수정본의 `item_no < 1 → bad_payload` 검증이 이걸 거부하므로,
그대로 배포하면 **직접입력 회차의 수정 저장이 막힌다.**
→ 아래 §6 핸들러에는 이미 하한을 0으로 고쳐 두었다 (`item_no < 0`으로 검사).

또한: 프론트가 **중복 item_no를 보낼 수 없음을 실증**했다
(17개 전 회차 × 공통+선택 트랙 전수 검사 0건, 직접입력 경로도 구조상 불가).
핸들러의 중복 검사는 방어용으로 유지한다.

## 4. 작업 순서 (이 순서를 지킬 것)

```
0) 백업                : responses·submissions 덤프 또는 스냅샷 확인
1) 진단 SQL 실행       : §5-1 — 원인 확정 + 실제 테이블·컬럼명 확보
2) (A) 중복 정리       : §5-2 (A) — rollback으로 건수 먼저 확인 → commit으로 재실행
                         ⚠️ (A)를 commit까지 마친 뒤에 (B)로. 순서 바꾸면 (B)가 중복 때문에 실패
3) (B) unique index    : §5-2 (B) — UPSERT의 전제조건
4) 핸들러 교체·배포     : §6 — [설정]·[확인필요] 지점을 진단 결과로 채워서
5) 검증                : §6 끝의 콘솔 스니펫 — 기대: saved === stored && stale_cleanup:"ok"
```

**안전 규칙** (기존 합의 유지):
- 데이터를 지우는 SQL은 실행 전에 형에게 건수·내용을 보여주고 확인받는다. 백업 먼저.
- service_role 키·토큰은 채팅·파일에 노출 금지(마스킹). 비밀번호·PIN 대신 입력 금지.
- 원인이 확정되기 전에는 배포하지 않는다.

## 5. SQL

### 5-1. 진단 (읽기 전용)

```sql
-- [0] DB 클라이언트 확인용: 함수 코드에서 createClient에 쓰는 키가
--     SERVICE_ROLE인지 ANON인지 눈으로 확인 (대시보드 → Edge Functions → api)

-- ① responses 실제 컬럼
select column_name, data_type, is_nullable
from information_schema.columns
where table_name = 'responses' order by ordinal_position;

-- ② RLS 켜짐 여부
select relname, relrowsecurity from pg_class
where relname in ('responses','submissions');

-- ③ 정책 목록 (delete/update 정책 유무)
select tablename, policyname, cmd, roles from pg_policies
where tablename in ('responses','submissions') order by tablename, cmd;

-- ④ responses를 참조하는 FK와 삭제 규칙 (RESTRICT/NO ACTION이면 삭제가 막힘)
select tc.constraint_name, tc.table_name, rc.delete_rule
from information_schema.table_constraints tc
join information_schema.referential_constraints rc on rc.constraint_name = tc.constraint_name
join information_schema.constraint_column_usage ccu on ccu.constraint_name = tc.constraint_name
where tc.constraint_type='FOREIGN KEY' and ccu.table_name='responses';

-- ④-2 트리거 확인
select tgname, tgrelid::regclass, tgenabled from pg_trigger
where tgrelid in ('responses'::regclass) and not tgisinternal;

-- ⑤ (회차,문항) 중복 — 나오면 (A) 필수
select submission_id, item_no, count(*) from responses
group by submission_id, item_no having count(*)>1 order by count(*) desc limit 20;
```

### 5-2. 수정

```sql
-- (A) 중복 정리 — ⑤에서 중복이 나왔을 때만. 먼저 rollback으로 건수 확인 → commit으로 재실행
begin;
  delete from responses r using responses r2
  where r.submission_id=r2.submission_id and r.item_no=r2.item_no and r.ctid<r2.ctid;
rollback;  -- ← 건수 확인 후 이 줄을 commit; 으로 바꿔 재실행 (반드시 (B)보다 먼저 확정)

-- (B) 핵심: UPSERT 기준 unique index
create unique index if not exists responses_sub_item_uniq
  on responses (submission_id, item_no);

-- 확인
select indexname, indexdef from pg_indexes where tablename='responses';
```

## 6. 교체 핸들러 (코워크 0812 수정본 + item_no 0 허용 반영)

기존 `api` 함수(index.ts)의 `/submit-update` 분기 전체를 교체.
`[설정]`·`[확인필요]` 표시 지점만 진단 결과로 채우면 된다.
`auth()` `cors()` `json()` `db` `digits()`는 기존 함수에 있는 것을 그대로 쓴다.

```ts
// [설정] 진단 ① 결과로 확정
const T_SUB   = "submissions";    // ✅ 확정
const T_RESP  = "responses";      // ⚠️ 미확인 — 실제 테이블명으로
const C_SUBID = "submission_id";  // ⚠️ responses 쪽 FK 컬럼명
const C_ITEM  = "item_no";        // ⚠️ 문항번호 컬럼명
const MAX_RESPONSES = 40, MY_ANSWER_MAX = 20, MEMO_MAX = 500;

if (path === "/submit-update" && req.method === "POST") {
  const H = cors(req.headers.get("origin") ?? "");

  const au = await auth(req);
  if (!au?.ok) return json({ ok: false, error: "unauthorized" }, 401, H);
  const myPhone = digits(au.phone);

  let body: any;
  try { body = await req.json(); }
  catch { return json({ ok: false, error: "bad_payload" }, 400, H); }

  const submission_id = String(body?.submission_id ?? "").trim();
  if (!submission_id) return json({ ok: false, error: "bad_payload" }, 400, H);

  const score = Number(body?.score);
  if (!Number.isFinite(score) || score < 0 || score > 100)
    return json({ ok: false, error: "bad_score" }, 400, H);

  const raw = Array.isArray(body?.responses) ? body.responses : null;
  if (!raw || raw.length < 1 || raw.length > MAX_RESPONSES + 1)  // +1: 직접입력 메타(0번) 여유
    return json({ ok: false, error: "bad_payload" }, 400, H);

  // UPSERT로 바뀌며 새로 필요해진 검사: 같은 item_no 중복 금지
  // (프론트는 중복을 못 보내는 걸 실증했지만 방어용으로 유지)
  const seen = new Set<number>();
  const rows: Record<string, unknown>[] = [];
  for (const r of raw) {
    const item_no = Number(r?.item_no);
    // ★ 하한 0: 직접입력(자유 시험)은 item_no 0 메타 레코드를 보낸다 (원안은 <1 이라 막혔음)
    if (!Number.isInteger(item_no) || item_no < 0 || item_no > MAX_RESPONSES)
      return json({ ok: false, error: "bad_payload", detail: "item_no" }, 400, H);
    if (seen.has(item_no))
      return json({ ok: false, error: "bad_payload", detail: "duplicate item_no" }, 400, H);
    seen.add(item_no);
    rows.push({
      [C_SUBID]: submission_id,
      [C_ITEM]:  item_no,
      result:    r?.result === "o" ? "o" : r?.result === "x" ? "x" : null,
      my_answer: r?.my_answer == null ? null : String(r.my_answer).slice(0, MY_ANSWER_MAX),
      memo:      r?.memo      == null ? null : String(r.memo).slice(0, MEMO_MAX),
      // [확인필요] /submit 이 더 넣는 컬럼이 있으면 여기에 동일하게 추가
      //   프론트는 area·unit·correct_answer·reached_step·reason·confidence 도 보낸다 (§8 참고)
    });
  }

  // 소유 확인 — 전화번호 기준
  // [확인필요] submissions에 phone이 직접 있는지 / 학생 테이블 경유인지
  const { data: sub, error: subErr } = await db
    .from(T_SUB).select("id, phone").eq("id", submission_id).maybeSingle();
  // (경유 버전) .select("id, students!inner(phone)") → digits(sub?.students?.phone)
  if (subErr) return json({ ok: false, error: "update_failed_lookup" }, 500, H);
  if (!sub)   return json({ ok: false, error: "not_found" }, 404, H);
  const ownerPhone = digits((sub as any).phone);
  if (!ownerPhone || ownerPhone !== myPhone)
    return json({ ok: false, error: "forbidden" }, 403, H);

  // 회차 본문 갱신 — updated_at 빠뜨리면 수정 이력이 사라진다
  const { error: upErr } = await db.from(T_SUB)
    .update({ score, updated_at: new Date().toISOString() }).eq("id", submission_id);
  if (upErr) return json({ ok: false, error: "update_failed_submission", detail: upErr.message }, 500, H);

  // ★ 응답 UPSERT — DELETE를 쓰지 않는다 (행 단위 원자적 → 답안 통삭제 창이 없다)
  const { error: upsertErr } = await db.from(T_RESP)
    .upsert(rows, { onConflict: `${C_SUBID},${C_ITEM}` });
  if (upsertErr) {
    const hint = upsertErr.code === "42P10"
      ? `UNIQUE INDEX (${C_SUBID}, ${C_ITEM}) 가 없습니다 — §5-2 (B) 를 먼저 실행`
      : upsertErr.message;
    return json({ ok: false, error: "update_failed_upsert", code: upsertErr.code, detail: hint }, 500, H);
  }

  // 안 보낸 문항 정리 — 실패해도 저장은 살리되 절대 조용히 넘기지 않는다 (유령 응답 방지)
  let stale_cleanup: "ok" | "failed" = "ok";
  const keep = rows.map((r) => r[C_ITEM] as number);
  const { error: delErr } = await db.from(T_RESP).delete()
    .eq(C_SUBID, submission_id).not(C_ITEM, "in", `(${keep.join(",")})`);
  if (delErr) {
    stale_cleanup = "failed";
    console.error("stale_cleanup_failed", { submission_id, code: delErr.code, msg: delErr.message });
  }

  // 검산 — saved !== stored 면 유령 응답 (델타 진단의 원천이 responses라 곧 오진)
  const { count: stored } = await db.from(T_RESP)
    .select(C_ITEM, { count: "exact", head: true }).eq(C_SUBID, submission_id);

  return json({ ok: true, submission_id, updated: true,
    saved: rows.length, stored: stored ?? null, stale_cleanup }, 200, H);
}
```

**오류 코드 표**: `unauthorized`(401) `bad_payload`(400) `bad_score`(400) `not_found`(404)
`forbidden`(403) `update_failed_lookup` / `update_failed_submission` / `update_failed_upsert`(500, 42P10=인덱스 없음)

## 8. 프론트가 보내는 데이터 (핸들러 컬럼 맞출 때 참고)

```json
{ "submission_id": "…", "score": 85,
  "responses": [ { "item_no": 1, "area": "수학Ⅰ", "unit": "지수함수와 로그함수",
    "my_answer": "3", "correct_answer": "3", "result": "o",
    "reached_step": null, "reason": null, "confidence": null, "memo": null } ] }
```

- 맞은 문항까지 **30개 전부** 보낸다 (마이페이지 통계가 이를 전제).
- `my_answer:""` = 오답만 체크 모드로 쓴 회차. `confidence:"찍음"` = 찍어서 맞음(`result:"o"`).
- 직접입력: `item_no:0` 메타 레코드 + 틀린 번호들(`result:"x"`), exam_code `자유:이름`.
